## エントリ1（2026-10-29）数値の表記ゆれによる誤 HOLD の対策

- 対象: `translator.py`（`NUMBER_RE`、`_numbers`、`_canonical_number` 新設）、`tests/test_hardening.py`（新規、テスト6件）
- 予測した不具合: 数値保持チェックが文字列の完全一致だったため、(a) 全角数字・全角句読点（２０２６年、１２．５％）は `．`／`％` がパターンに合わず断片化して抽出され、半角で返る訳文と一致せず誤って HOLD になる、(b) 桁区切り `10,000`→`10000`、小数末尾0 `12.50`→`12.5`、％前の空白 `12.5 %` のような「同じ数の別表記」でも誤って HOLD になる。実測で再現を確認（修正前: `_numbers('２０２６年に１２．５％増えた') == ['２０２６', '１２', '５']`）。
- 改善案: (1) 抽出前に全角→半角の正規化コピーを使う、(2) 抽出値を Decimal で正規化した正規形（桁区切り除去・小数末尾0除去・小数カンマ／欧州式桁区切りの解釈・％有無の統一）で比較する、(3) 値そのものが変わった場合（12.5→12.6）は従来どおり HOLD を維持する。
- 実装: 上記 (1)(2)(3) を実装。`%` の前の空白も許容するよう `NUMBER_RE` を調整。
- 動作確認: 全テスト62件（従来56＋新規6）を3回とも成功。`py_compile` 成功。実モデル検証は未実施。
- 残課題: 漢数字（二〇二六年、三割など）は今回も対象外（抽出されず、脱落しても検出できない）。

## エントリ2（2026-10-29）段落区切りが翻訳結果で失われる問題の対策

- 対象: `translator.py`（`translate_document`）、`tests/test_hardening.py`（テスト3件追加）
- 予測した不具合: `translate_document` は全文を文のリストに平坦化し、訳文を `'\n'.join` で連結していたため、空行で区切られた段落構造が常に失われ、複数段落の文書が1段落になって返る。実測で再現を確認（修正前: `学习软件。\n\n网络运行。`（繁體字出力）→ `學習軟體。\n網路執行。`）。
- 改善案: (1) 段落単位に処理し段落内は従来どおり文単位、段落間は空行で連結する、(2) 文ごとの結果リスト（API応答の `sentences`）は従来の平坦な形を維持して互換性を保つ、(3) 段落が3つ以上・空行が連続する場合でも区切り数を保存する。
- 実装: 上記 (1)(2)(3) を実装。1段落のみの入力では従来と同一の出力になる。
- 動作確認: 全テスト65件（従来62＋新規3）を3回とも成功。`py_compile` 成功。実モデル検証は未実施。
- 残課題: 段落内の単一改行（改行のみで区切られた行）は従来どおり文の一部として扱われ、行区切りとしては保存されない。

## エントリ3（2026-10-29）用語集の英字キーが単語内部に誤適用され、未復元トークンが漏れる問題の対策

- 対象: `translator.py`（`_protect_glossary`、`_protect` の TECH フィルタ）、`tests/test_hardening.py`（テスト4件追加）
- 予測した不具合: 用語集キーが部分文字列で置換されるため、キー `AI` が `AIDS` の内部にも適用され単語が壊れる。さらに置換後の内部トークン＋残りの文字（`ZZTERM0001ZZDS`）が技術名として丸ごと保護され、単一パスの復元では内部トークンが復元されず、未復元の `ZZTERM…ZZ` が訳文に残る。実測で再現を確認（修正前: `AI技术与AIDS防治`＋用語集 `AI=人工智能` → `人工智能技术与ZZTERM0001ZZDS防治`）。
- 改善案: (1) 先頭・末尾が ASCII 英数字の用語集キーは ASCII 単語境界の内側でのみ一致させる（CJK キーは複合語内の部分一致を従来どおり維持）、(2) 技術名保護は、内部トークンを「含む」スパンも保護対象から外す（従来はトークンそのものと完全一致する場合のみ除外）。
- 実装: 上記 (1)(2) を実装。
- 動作確認: 全テスト69件（従来65＋新規4）を3回とも成功。再現ケースの出力が `人工智能技术与AIDS防治` になることを直接確認。`py_compile` はサイクル5で一括確認。実モデル検証は未実施。
- 残課題: キーの途中だけが ASCII の混在キー（例: `AI技術`）は先頭側だけ境界を課す現在の仕様で十分か、実例が出たら再検討する。

## エントリ4（2026-10-29）メールアドレスが保護対象でなくモデルに渡される問題の対策

- 対象: `translator.py`（`PROTECT_PATTERNS`）、`README.md`（保持チェック一覧にメールアドレスと、エントリ1の数値正規化の注記を追加）、`tests/test_hardening.py`（テスト2件追加）
- 予測した不具合: URL は保護されるのにメールアドレスは保護パターンに無く、本文の一部としてモデルへ渡される。モデルが翻訳・音訳・脱落させる可能性があり、脱落しても技術名チェック（大文字混在パターン）には通常かからないため検出もできない。実測で再現を確認（修正前: `_protect('連絡は contact@example.com まで', …)` の対応表は空）。
- 改善案: (1) メールアドレスのパターンを URL と同様に保護対象へ追加し、モデルには渡さず原文のまま復元する、(2) 逆翻訳側でも同じ保護が効く（共通の `PROTECT_PATTERNS` を使用しているため自動的に適用される）、(3) README の保持チェック一覧へ明記する。
- 実装: 上記 (1)(3) を実装（(2) は共通パターンのため追加作業なしに対象になることをテスト範囲で確認）。
- 動作確認: 全テスト71件（従来69＋新規2）を3回とも成功。モデルへの入力に `@` が含まれないこと・訳文にアドレスがそのまま残ることをスタブで確認。`py_compile` 成功。実モデル検証は未実施。
- 残課題: `www.example.com` のようなスキームなし URL 表記、`@` を含む SNS ハンドルは今回も保護対象外。

## エントリ5（2026-10-29）簡繁字残留チェックの文字セット不足の対策

- 対象: `translator.py`（`SIMPLIFIED_ONLY_CHARS`／`TRADITIONAL_ONLY_CHARS` に189ペア追加）、`tests/test_hardening.py`（テスト3件追加）
- 予測した不具合: 正規化後も残った「指定と異なる字形固有文字」を HOLD にする安全網（`SCRIPT_MISMATCH`）の文字セットが約108字しかなく、頻出の簡体字専用字が抜けていた。実測で再現を確認（修正前: `让人们认识这条河边` を繁體字出力として検査すると、検出は 们・认・这 のみで 让・识・边 が素通り）。
- 改善案: (1) 候補字を機械的に検証してから追加する（OpenCC の s2t で1字の異なる字へ変換され、t2s で元へ戻るペアのみ採用）、(2) 繁體字文にも現れ得る曖昧な字（发・复・余・后・吃・叶・于 など）は候補から除外し誤 HOLD を避ける、(3) セット全体（既存分を含む）が同じ検証を満たすことをテストで継続確認する。
- 実装: 上記 (1)(2) で189ペアを追加（簡体字側・繁體字側とも）。検証はテスト `test_residual_pairs_are_opencc_consistent` として組み込み済み。
- 動作確認: 全テスト74件（従来71＋新規3）を3回とも成功。当初、期待値の書き誤り（共有字 人・河・格 を検出対象に含めた等）で新規テストが3回失敗し、いずれも実装ではなくテスト側の誤りと確認して修正した。`py_compile` 成功（translator.py／app.py／scripts/verify_models.py）。実モデル検証は未実施。
- 残課題: それでも網羅ではない（頻出候補からの拡張のため）。漢数字と同様、検出できない残留はあり得る前提で、OpenCC 正規化そのものが主防御という位置づけは変わらない。
